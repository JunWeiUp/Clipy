# 同步能耗优化方案

## 一、目标与硬约束（用户已确认）

- **纯局域网**：不引入云端 / FCM，保持当前定位与隐私模型。
- **秒级接收**：Android 在后台/灭屏时，Mac 推送必须在秒级到达。
- **目的**：在满足上述前提下降低整体能耗。

## 二、核心结论（必须先认知的物理边界）

在「纯局域网 + 秒级接收」两个硬约束**同时成立**时，Android 端的 `PARTIAL_WAKE_LOCK`（[ClipySyncForegroundService.kt:53-60](file:///Users/mac/Documents/code1/clipy1/clipy_android/android/app/src/main/kotlin/com/clipyclone/clipy_android/ClipySyncForegroundService.kt#L53-L60)）**无法被移除**。

原因：Android Doze 会冻结 CPU 与应用事件循环。纯局域网内没有任何机制能在 Doze 下实现「秒级」唤醒——
- WoL magic packet：Android WiFi 不会因此唤醒 CPU；
- BLE scan：Doze 下会被系统延迟到维护窗口（约 10–25min 一次），非秒级；
- 持久 TCP + 内核 keepalive：连接活着，但 Dart `await for` 仍被冻结到维护窗口；
- `AlarmManager.setExactAndAllowWhileIdle`：被限流到约每 9min 一次。

唯一能在 Doze 下秒级唤醒 app 的是 FCM 高优先级推送，已被约束排除。

**因此本方案的真实目标**：保留 wake lock，但把它「之外」的所有能耗压到接近零，并让「持锁态」本身的 CPU 真正闲置（让 CPU 在中断之间进入轻量 idle）。同时提供**可选 Eco 模式**作为「愿意放弃秒级延迟」时的省电逃生口。

> 说明：若未来用户放宽到「分钟级可接受」，则可以彻底去掉持续 wake lock，改用 WorkManager 周期窗口拉取。本计划在改动 7 预留这个开关。

## 四、改动项（按收益/风险排序）

### 改动 1 · 取消稳态主动探活，折叠进发送路径【最大非 wake-lock 收益】

**What**：移除 macOS 与 Android 各自的 120s 周期探活定时器。改为：**仅在「有数据要发」或「UI 需要展示在线列表」时**才探活/连接。

**Why**：稳态下双方都没数据要发，每 120s 各做一次 TCP connect 纯属浪费。把探活并入发送路径后，空闲期网络活动趋近于零。

**How**：
- macOS：`probeDiscoveredPeers()`（[SyncManager.swift:711](file:///Users/mac/Documents/code1/clipy1/clipy_macos/Sources/SyncManager.swift#L711)）的定时调用改为「按需触发」——在 `sendSync` 前直接尝试发送（见改动 3），失败再走驱逐逻辑。
- Android：`sync_manager.dart` 的 `_peerLivenessInterval` 定时器移除周期触发，同样并入发送路径。
- 保留一个**低频 UI 刷新探活**（见改动 4），仅用于菜单/设备列表显示，与发送解耦。

### 改动 2 · 探活定向化（仅发送方探活）

**What**：探活只由「有数据要发的那一侧」发起；接收方不主动探活发送方。

**Why**：当前两侧各自维护对对方的探活定时器，对同一链路做了两次探测。删除冗余方向可减半探活流量。

**How**：在改动 1 的基础上自然成立——周期探活被取消后，只有发送方在发送时做一次探测。接收方在线与否由「收到数据」本身证明，无需反向探活。UI 列表的对方在线状态由改动 4 的低频刷新 + 收发事件驱动更新。

### 改动 3 · 合并探活与发送（单连接 doing both）

**What**：发送方不再「先 probe → 等成功 → 再 send」，而是直接 `connect + send`。连接成功即说明对端在线；失败即触发「失败处理」（见改动 5）。

**Why**：当前 probe 与 send 是两次独立 TCP 连接，多一倍握手开销 + 一次额外 RTT。合并后每次发送只建一次连接，且空闲时零连接。

**How**：在 `sendSync`（[SyncManager.swift:2014](file:///Users/mac/Documents/code1/clipy_macos/Sources/SyncManager.swift#L2014)）与 Android 对应发送方法中，去掉「先 probe」的前置步骤，直接尝试建连+发送；在连接 `.failed` / 超时分支里调用 `recordPeerMiss`（[SyncManager.swift:784](file:///Users/mac/Documents/code1/clipy_macos/Sources/SyncManager.swift#L784)）。

### 改动 4 · 轻量 UI 刷新探活（5 分钟，仅更新列表）

**What**：单独的低频定时器（macOS 5min，Android 5min），只为了刷新菜单/设置页里的设备在线状态，不影响发送。

**Why**：用户需要看到对方在不在线，完全去掉定时器会让列表过期。5 分钟足以满足 UX，远比 120s 省。

**How**：新建一个 `refreshPeerPresenceForUI()`，复用 `probePeer`（[SyncManager.swift:747](file:///Users/mac/Documents/code1/clipy_macos/Sources/SyncManager.swift#L747)）但频率 300s。Android 侧同理。注意：这个探活**不阻塞发送**——发送走改动 3 的即时路径。

### 改动 5 · 发送可靠性增强（保证「需要时能收到」）

**What**：发送失败时，做一次**按需子网重扫 + 有限重试**，并把所有消息类型纳入「待投递队列 + ack」机制（目前仅 notification 类型有 ack）。

**Why**：用户明确要求「需要发消息时对方能收到」。取消周期探活后，peer 可能暂时不在列表里（如对端 IP 变化、从睡眠刚醒），需要发送时即时发现。

**How**：
- macOS `sendSync` 失败分支：调用 `scanSubnets()`（[SyncManager.swift:1326](file:///Users/mac/Documents/code1/clipy1/clipy_macos/Sources/SyncManager.swift#L1326)）+ `connectManualPeers()` 重发现，然后重试发送（最多 2 次，间隔 500ms）；仍失败则入待投递队列。
- 把现有 notification 的 `pendingSync` + `notification/ack` 模式（`notification_manager.dart:184-201`）推广到 `text/plain`、`file/*` 类型：发送方落盘待投递队列，收到对端 ack 才删除；每次 peer 上线/重连时 flush 队列。
- 收端在 `processReceivedData`（[SyncManager.swift:1123](file:///Users/mac/Documents/code1/clipy_macos/Sources/SyncManager.swift#L1123)）对所有类型回一个轻量 ack 帧。

### 改动 6 · Android 持锁态稳态审计【压低 wake lock 的边际成本】

**What**：审计并移除 Android 端空闲期所有周期性定时器/轮询，让持锁态下 Dart 事件循环真正闲置（CPU 在中断间进入轻量 idle）。

**Why**：wake lock 让 CPU 不进 deep sleep，但如果事件循环里还有定时器在跑，CPU 会持续被拉回 active。清除空闲定时器后，持锁态的功耗主要由「CPU 浅睡 + 网卡中断」构成，显著低于「持锁 + 空转」。

**How**：
- 移除改动 1 涉及的 `_peerLivenessInterval` 定时器。
- 排查并确认 `sync_manager.dart` / `notification_manager.dart` 中无其它周期 Timer（如剪贴板轮询、心跳广播）。
- 确认 `ClipyNotificationListenerService` 是系统回调驱动（非轮询），无需改动。
- 目标：同步开启且无收发时，Android 端零定时器、零网络活动，唯一活动是等待入站 TCP 中断。

### 改动 7 · 可选 Eco 模式（默认关闭，省电逃生口）

**What**：新增偏好项「省电模式」。开启后，当**双方均灭屏超过 N 分钟（默认 10min）且无近期复制活动**时，Android 释放 wake lock、停掉 listener，转为 WorkManager 每 15min 周期窗口短暂唤醒拉取待投递队列。任一端亮屏/发生复制时立即恢复持续模式。

**Why**：在用户接受「深夜/长时间不用时分钟级延迟」的场景下，彻底消除 wake lock 持续能耗。默认关闭以遵守「秒级」硬约束。

**How**：
- `PreferencesManager` / Flutter 侧偏好新增 `ecoMode` 开关与 `ecoIdleThreshold`。
- Android：`PowerManager` 屏幕状态广播（`ACTION_SCREEN_OFF/ON`）+ Mac 端 `NSWorkspace` 睡眠/唤醒（已有，[SyncManager.swift:445](file:///Users/mac/Documents/code1/clipy1/clipy_macos/Sources/SyncManager.swift#L445)）协同判断。
- Eco 状态下用 `WorkManager` 周期任务拉取（需 Mac 侧暴露一个 `pull/pending` 请求类型）；恢复持续模式时 flush。
- 设置页加说明文案：开启后后台接收延迟可能达 15 分钟。

### 改动 8 ·（调研项，默认不实施）持久连接 + SO_KEEPALIVE

**What**：配对设备间维护一条长连接 + 内核 TCP keepalive，替代每消息短连接。

**Why（评估）**：省去每次发送的 connect 握手；内核级 keepalive 比 app 探活便宜。**但**：Doze 下 Dart 事件循环仍冻结，无法让 Android 秒级接收，**不解决 wake lock**；且会引入连接管理复杂度（断线重连、跨频段切换）。

**决策**：当前每消息短连接 + 已优化的发送路径已足够；持久连接收益有限且复杂度高，**本计划不实施**，仅记录评估结论。

## 五、假设与决策

1. **wake lock 保留**：硬约束下的唯一选择，已在第二节论证。
2. **优先实施改动 1–6**（纯收益、低风险、不改变秒级保证）；**改动 7 作为可选**；改动 8 不做。
3. **不引入 mDNS 回退**：跨频段多播隔离问题依旧（[SyncManager.swift:1164-1171](file:///Users/mac/Documents/code1/clipy_macos/Sources/SyncManager.swift#L1164-L1171) 注释），保持当前「ARP 过滤子网扫描 + 手动配对 + 端点缓存」发现体系。
4. **加密不变**：仍用 AES-GCM + 预共享密钥（[SyncManager.swift:190-196](file:///Users/mac/Documents/code1/clipy_macos/Sources/SyncManager.swift#L190-L196)）。新增 ack/pending 帧走同一加密通道。
5. **向后兼容**：改动 5 的 ack 机制需双端版本一致；设计为「收端不回 ack 时发送方仍按现有逻辑工作」，避免强制同步升级。

## 六、验证步骤

1. **编译**：macOS 端 `xcodebuild` 编译通过；Android 端 `flutter build apk` 通过。
2. **空闲态网络活动**：配对成功且无操作 10 分钟，用 `tcpdump` / Wireshark 抓包，确认两端**无周期 TCP probe**，仅每 5min 一次 UI 刷新探活。
3. **发送即时性**：Mac 复制文本，观察 Android 后台秒级收到（保持当前体验）；反向 Android 通知→Mac 同样秒级。
4. **可靠性**：Android 灭屏进入 Doze 后，Mac 发送文本 → 秒级收到（验证 wake lock 仍生效）；断开 Android WiFi 5s 再恢复，Mac 发送应触发改动 5 的重扫+重试并最终送达。
5. **Android 稳态功耗**：Android Studio Energy Monitor / `dumpsys batterystats` 对比改动前后：稳态 CPU 占用下降，待机电流下降（wake lock 仍在，但空转减少）。
6. **Eco 模式（若启用）**：双方灭屏 >10min，确认 wake lock 释放、待机电流显著下降；亮屏后恢复秒级接收。
7. **UI 在线状态**：设备列表在 5min 内反映对端离线/在线，无明显长期过期。
