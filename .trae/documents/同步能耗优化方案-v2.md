# 同步能耗优化方案 v2（持久连接 + 可靠投递 + 去定时器）

> 本计划承接 `同步能耗优化方案.md`（改动 1/4/5-Layer1 已落地），在用户进一步明确「**尽可能去掉定时器，设备列表改为打开页面时刷新**」后，重新确定主攻方向。v2 取代 v1 的剩余执行顺序（v1 第八节步骤 5-8）。

## 一、目标与硬约束（不变）

- **纯局域网**：不引入云端 / FCM。
- **秒级接收**：Android 后台/灭屏时，Mac 推送秒级到达。
- **目的**：在前两条前提下，把能耗压到物理下限，并保证「需要发消息时对方能收到」。

## 二、核心决策（基于用户选择）

1. **持久连接重构**：配对设备间维护长连接 + TCP keepalive，连接状态即在线状态。
2. **可靠投递**：把 ack + 持久化待投递队列推广到 `text/plain`。
3. **去定时器**：移除周期性 peer 探活；设备列表改为页面打开时按需刷新；剪贴板轮询与通知健康监控改为前台态运行。

### 关键可行性结论（修正 v1 对持久连接的误判）

v1 改动 8 以「Doze 下 Dart 事件循环冻结，持久连接无法秒级接收」为由否决了长连接。**该前提在本项目不成立**：Android 端持有 `PARTIAL_WAKE_LOCK` + 前台服务（`ClipySyncForegroundService.kt:53-60`），进程与事件循环不会被 Doze 冻结。因此持久连接在 wake lock 保护下**可以**秒级收发，并能：
- 彻底移除 300s peer 探活（连接在即在线）；
- 消除每条消息的 connect 握手；
- 让空闲态网络活动趋近于「内核 keepalive（每 60s 一个空包）」。

## 三、现状（已落地部分，执行前提）

- macOS `SyncManager.swift`：300s `peerPresenceInterval` UI 探活（L126, L638-647）；`sendSync` 直连+发送，失败走 `rescanThenRetry`（L1772-1809）；POSIX IPv4 listener 的 `posixHandleClientReadable`（L956）已**循环 recv**，天然支持单连接多帧。
- Android `sync_manager.dart`：300s `_peerPresenceInterval`（L198, L462-467）；`_sendSync` 直连发送（L1683）；`_handleConnection`（L728）`await for (data in socket)` 已**循环读取**，天然支持单连接多帧。
- 待投递队列：双端均为 30s 内存队列（macOS `pendingQueue` L183, Android `_pendingQueue` L185），`text/plain`/`file/*` 无 ack。
- 通知已具备 ack + 持久化（`notification_manager.dart:184-201`，`NotificationRepository.insertPendingSync`）。

## 四、连接拓扑设计（重要）

采用**双向独立出站**模型，避免在入站 fd 上回写发送数据的复杂度：

- 每一侧对自己「发现的 peer」维护一条**出站持久连接**（outbound），用于本侧发送。
- 对端的出站连接落在本侧的 listener 上，本侧 listener 已循环读取 → 用于接收。
- 一对设备最多存在 2 条连接（每方向一条），LAN 内 keepalive 成本可忽略；**无需去重**。
- 在线状态：本侧有该 peerId 的活跃出站连接 = 在线；本侧 listener 上有该 peerId 的活跃入站连接（握手后已知 peerId）= 对端可达。任一方向存在即视为在线，断开即触发重连。

## 五、改动项

### 改动 A · 持久出站连接（核心）

#### A-1 macOS `SyncManager.swift`

**新增状态**（confined to `syncQueue`）：
```swift
private var persistentConnections: [String: NWConnection] = [:]  // peerId -> outbound
private var reconnectBackoffs: [String: TimeInterval] = [:]       // peerId -> next delay
private static let keepaliveIdle: TimeInterval = 60
private static let keepaliveInterval: TimeInterval = 60
private static let maxReconnectBackoff: TimeInterval = 30
```

**改造 `performHandshake`（L1376-1434）**：握手成功（收到 hi）后，不再 `connection.cancel()`，而是：
1. 通过 `NWProtocolTCP.Options` 启用 keepalive（`enableKeepalive=true, keepaliveIdle, keepaliveInterval`）——需在创建 NWConnection 时用 `NWParameters(tcp:nil, tcpOptions:)` 传入；
2. 把 connection 存入 `persistentConnections[remotePeerId]`（`handleHandshakeHi` 已给出 peerId）；
3. 重置 `reconnectBackoffs[peerId] = 0`；
4. 启动常驻接收循环（复用 `receiveMessage(from:)` L1064 的递归 receive 模式）处理入站帧，并在 `.failed/.cancelled`/对端 EOF 时调用 `teardownPersistentConnection(peerId:)`。

**改造 `sendSync`（L2054-2134）**：
- 首参 `targetPeerId` 命中 `persistentConnections` 且连接存活 → 直接 `connection.send(lengthPrefix+data)`，不再新建 NWConnection、不再走 connect 超时分支；
- 未命中 → 走 `performHandshake`（等价于建立持久连接）再发送；建立失败维持现有 `handleSendEstablishmentFailure`（但 rescan 后重试也复用持久连接路径）。

**新增 `teardownPersistentConnection(peerId:)`**：
- 从 `persistentConnections` 移除并 cancel；
- 从 `discoveredPeers` 移除（标记离线）+ UI 通知；
- 调度 `scheduleReconnect(peerId:)`（指数退避：1s→2s→4s→…→`maxReconnectBackoff`，网络变化/页面打开时立即重试并清退避）。

**`scheduleReconnect`**：复用 `connectManualPeers` + 针对该 peerId 的端点缓存/驱逐端点直连 + 必要时 `scanSubnets`。

**移除周期探活**：删除 `start()` 中 `startPeerPresenceProbing()` 调用（L505）；保留方法体以便显式调用，但**不再挂定时器**。在线状态改为读 `persistentConnections`。

**POSIX listener 接受侧 keepalive**：`posixArmClient`（L938）在 set nonblock 之后追加 `setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, ...)`（macOS 可用 `TCP_KEEPALIVE` 设间隔）。

#### A-2 Android `sync_manager.dart`

**新增状态**：
```dart
final Map<String, Socket> _persistentConnections = {};  // peerId -> outbound
final Map<String, int> _reconnectBackoffSec = {};
static const int _keepaliveIdleSec = 60;
static const int _maxReconnectBackoffSec = 30;
```

**改造 `_performHandshake`（L1138-1173）**：握手成功后不 `socket.destroy()`，改为：
1. 启用 keepalive：`socket.setOption(RawSocketOption(SOL_SOCKET, SO_KEEPALIVE, ...))`（执行时确认 Dart `RawSocketOption`/`Socket.setRawOption` 在目标 API level 可用，Android 也支持 `tcpKeepaliveInterval`）；
2. `_persistentConnections[peerId] = socket`；`_reconnectBackoffSec.remove(peerId)`；
3. 启动接收循环（复用 `_handleConnection` 的 `await for (data in socket)` 模式）处理入站帧，catch/finally 触发 `_teardownPersistentConnection(peerId)`。

**改造 `_sendSync`（L1683-1699）**：
- `_persistentConnections[peerId]` 存活 → `_writeFrame` 直接写；
- 否则先 `_performHandshake`（建立持久连接）再写；失败维持 `_rescanThenRetry`。

**新增 `_teardownPersistentConnection` / `_scheduleReconnect`**：对称于 macOS，指数退避重连，复用 `_connectManualPeers`/`_scanSubnets`。

**移除周期探活**：`start()` 中不再调用 `_startPeerPresenceProbing()`（L562）；`_stopPeerPresenceProbing` 保留。在线状态改为 `_persistentConnections.containsKey(peerId)`。

#### A-3 设备列表按需刷新（双端）

- **不再有定时器**驱动设备列表。
- 设备列表页 `initState`/`onAppear`/`viewWillAppear` 调用 `refreshDiscovery()`（已存在，macOS L570 / Android L669），它做一次性扫描并建立/刷新持久连接。
- 列表的「在线/离线」实时反映 `persistentConnections`/`_persistentConnections` 状态变化（连接建立与断开已有 UI 通知路径，复用 `notifyPeersChanged`/`_notifyPeersChanged`）。

### 改动 B · 可靠投递（ack + 持久化，针对 text/plain）

#### B-1 通用 ack 帧

新增消息类型 `message/ack`（载荷 `{}`，用 `hash` 字段对齐被确认帧），**向后兼容**：旧端收到未知类型直接忽略（双端 `processReceivedData`/`_handleSyncMessage` 的 `default` 分支已安全）；发送方收不到 ack 时按 TTL 过期清理，最坏情况是重投递，由现有 `handleRemoteSync` 的 hash 去重兜底。

#### B-2 接收侧回 ack

- macOS `processReceivedData`（L1124）`case "text/plain"`：`handleRemoteSync` 后，通过现有 `reply` 闭包回发一个 `message/ack`（hash=message.hash）。`file/chunk` 在 `isLast` 为真时回 `message/ack`（hash=fileId）。
- Android `_handleSyncMessage`（L812）`text/plain`：`handleRemoteSync` 后经当前 socket 回写 `message/ack`；`file/chunk` `isLast` 同理。

#### B-3 发送侧持久化 + 收 ack 删除

- **macOS**：新增轻量 `PendingSyncStore`（JSON 文件 `pendingSync.json`，条目 `{hash, content, type, targetPeerId, ts}`，per-peer 上限 50、TTL 24h）。`broadcastSync`/`sendTextToPeer` 发 `text/plain` 时：写入 store → 发送。新增 `handleMessageAck(hash:)` 删除对应条目。持久连接（重）建立时 `flushPendingSync(forPeerId:)` 重投。
- **Android**：复用 `NotificationRepository` 模式，新增/泛化 `PendingSyncRepository`（SQLite，兼容现有 `pendingSync` 表）。`broadcastSync`/`sendTextToPeer` 写入 → 发送；`message/ack` 命中删除；`_recordDiscoveredPeer`（L886）连接建立时 flush。
- **file**：不持久化字节（体积大、频率低），可靠性由持久连接 + 现有「写失败即中止」保证；仅用 `isLast` 的 ack 让发送方记录成功。

#### B-4 处理 message/ack

- macOS `processReceivedData` 新增 `case "message/ack": handleMessageAck(message.hash)`。
- Android `_handleSyncMessage` 新增 `else if (message.type == 'message/ack') handleMessageAck(message.hash)`。
- `notification/ack` 维持现状（兼容）。

### 改动 C · 去定时器（前台态化）

| 定时器 | 位置 | 处理 |
|---|---|---|
| 300s peer 探活 | macOS L638 / Android L462 | **删除周期触发**（见改动 A）。探活方法保留供 `refreshDiscovery()` 显式调用。 |
| 剪贴板轮询 1s/5min | `clipboard_manager.dart` L74/L153/L161 | **改为前台态**：`AppLifecycleState.resumed` 启动 1s 轮询；`paused` 停止。依据：Android 10+ 已限制后台读取剪贴板，后台 5min 轮询本就大概率无效应属浪费。回到前台时立即 poll 一次补齐。 |
| 通知健康监控 45s/5min | `notification_health_monitor.dart` L44-101 | **改为前台态**：仅在 resumed 时运行；灭屏/后台停止周期检查，改为页面打开时做一次健康判定。 |
| 文件清理 30s | sync_manager L651 | **不变**：仅在 `_pendingFiles` 非空时创建，空闲态不存在，零成本。 |

结果：Android 后台稳态 = **零应用层定时器**；唯一活动是内核 TCP keepalive（每 60s）+ 等待入站 socket 中断。macOS 同理（无 peer 探活、无 keepalive 之外的周期）。

## 六、假设与决策

1. **wake lock 保留**（秒级硬约束下的唯一选择，v1 已论证）。
2. **持久连接拓扑采用双向独立出站**，避免在 POSIX 入站 fd 上回写发送数据；每对设备最多 2 条连接，LAN 内可忽略。
3. **不持久化 file 载荷**：体积大频率低，持久连接 + 写失败检测足够；仅回 file-complete ack。
4. **向后兼容**：`message/ack` 未被对端识别时，发送方按 TTL（24h）清理并多次重投，hash 去重保证幂等。
5. **keepalive 间隔 60s**：显著短于 ARP/Doze 维护窗口，足够早发现半开连接；能量代价极低（空 ACK 包）。
6. **剪贴板后台轮询去除的安全性**依赖 Android 10+ 的后台剪贴板访问限制；若目标设备 <API29，回前台时立即补 poll 仍能覆盖该场景。

## 七、验证步骤

1. **编译**：macOS `swiftc -typecheck Sources/*.swift Sources/UI/*.swift`（参照 `build_macos_app.sh`）；Android `flutter analyze` + `flutter build apk`。
2. **空闲抓包**：配对成功后双方无操作 10min，`tcpdump`/Wireshark 确认**仅**每 60s keepalive 空包，无应用层周期 probe、无子网扫描。
3. **持久连接复用**：连续发送 5 条文本，抓包确认仅在首条有一次握手，后续复用同一连接。
4. **断线重连**：关闭 Android WiFi 5s 再恢复，确认 macOS 出站连接在 keepalive 内检测断开、退避重连成功；反向同理。
5. **可靠投递**：Android 灭屏（对 Mac 不可达）>30s，Mac 发送文本 → Android 恢复后**秒级收到**且无丢失（验证持久化待投递队列）。收到后 Mac 收到 `message/ack` 并从 store 删除。
6. **设备列表按需刷新**：列表页打开即触发扫描并准确反映在线状态；关闭页面 10min 内无任何后台探活流量。
7. **去定时器审计**：Android `dumpsys alarmmanager`/`jobscheduler` 在 app 后台时无本应用周期条目（仅 FGS/wake lock）。
8. **Android 稳态功耗**：`dumpsys batterystats` 对比 v1：后台稳态 CPU 唤醒次数下降。

## 八、执行顺序（建议）

1. **改动 A 双端持久连接**（最大收益、最大改动；先做以解锁后续验证基线）。
2. **改动 C 去定时器**（在 A 验证连接状态可替代探活后，删除周期触发 + 前台态化）。
3. **改动 B 可靠投递**（在 A/C 稳定后叠加 ack + 持久化）。
4. **按第七节逐项验证**。
